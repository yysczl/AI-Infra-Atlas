# 一条聊天消息背后，究竟有多少台机器在忙？

*从一条聊天请求出发，讲清 Transformer、GPU、推理引擎、分布式训练和线上服务是怎样接在一起工作的。*

你给聊天机器人发了一句话：“帮我解释一下，为什么大模型有时回答得很慢？”

顺利的时候，输入框刚刚清空，答案就开始往外冒。忙的时候，页面转了好几秒才出现第一个字。还有一种情况更奇怪：前半句出来得很快，后半句却像挤牙膏，每隔一会儿才多几个字。

这三种体验，背后可能是三种完全不同的性能问题。请求到达服务器之后，可能在排队；开始计算之后，可能花了不少时间处理输入；真正开始输出之后，GPU 又得一轮接一轮地生成新内容。如果有几百个人同时提问，服务器还得决定把哪些人的工作放到一起做，哪些人暂时等一等。

把模型训练出来是一件事，让它稳定地为很多人提供服务，是另一整套工程。后面这套工程通常被称为 **AI Infra（AI Infrastructure，人工智能基础设施）**。它涉及 GPU 和网络这样的硬件，也涉及 CUDA、PyTorch、vLLM、Kubernetes 等软件。单看名字很容易觉得杂，顺着一条请求的经历看，许多技术其实是被一个接一个的实际问题逼出来的。

## 1. 消息发出去了，模型怎么还没开始算？

先看聊天页面背后的服务。

浏览器把文字组织成一个 HTTP 请求，发到服务器的某个 API（应用程序编程接口）。如果这是一个与 OpenAI 接口兼容的聊天服务，客户端可能调用 `POST /v1/chat/completions`，把 `messages`、模型名称、温度和最大生成长度等参数放在请求体里。“OpenAI API 兼容”让不同服务端采用相近的请求格式，客户端也就更容易在不同模型服务之间切换。

请求到达入口后，**API Server** 先完成参数检查、权限校验等工作。很多产品还会在这一层处理身份认证、流量限制（Rate Limiting）和超时控制。输入合法，才会进入后面的执行链路。

接下来出现了第一个麻烦：假设一张 GPU 上已经有四个人在生成回答，第五个人此时也来了。GPU 的计算单元也许还没用满，但负责保存上下文的显存已经很紧张。新请求就得先排队。

实际系统往往有一个 **Scheduler（调度器）**。它根据当前请求的长度、剩余计算预算、显存可用量等信息，决定这一轮让谁执行。选中的请求交给 **Worker**，也就是实际持有模型、调用 GPU 完成计算的执行进程。API Server、调度器与 Worker 的进程边界，取决于具体框架和部署方式。

把过程画出来，大致是这样：

```text
浏览器 / App
    │  HTTP / API
    ▼
网关 / 负载均衡
    │
    ▼
API Server ── 参数检查、鉴权、限流
    │
    ▼
等待中的请求 ── Scheduler 决定下一轮执行谁
    │
    ▼
Worker / 模型执行引擎
    │
    ▼
GPU：计算输出 Token
    │
    ▼
流式返回 ── 页面逐渐出现文字
```

你在网页上看到文字一个个出现，通常来自**流式输出（Streaming）**。服务端不等整段回答生成完毕，就不断把已生成的内容送回客户端。HTTP 场景里常用 **SSE（Server-Sent Events）** 把这些增量传回去。客户端收到的可能是一段文本片段，也可能要等若干个 Token 凑成可显示的文字才刷新页面。

**用户看到的等待时间，包含了很多 GPU 计算之外的开销。** 这条链路后面还会反复出现。

比如同一条请求花了 3 秒才开始显示文字，可能是排队 2.5 秒、模型计算 0.5 秒；也可能完全没排队，模型用了 3 秒处理一份很长的输入。两种情况在聊天窗口里看起来差不多，调优方法却完全不同。推理服务之所以需要专门的调度器、缓存管理和监控，就是为了把这几段时间拆开处理。

## 2. 一句话怎样变成模型能够计算的数字？

现在假设排队结束，轮到这条请求执行了。

我们在聊天框里输入的是文字，模型内部处理的是数值。第一步由 **Tokenizer（分词器）** 完成，它根据自己的词表（Vocabulary），把输入变成一串 **Token**。一个 Token 可能对应单词、常见词组、一个汉字，也可能只是某个词的一部分。每个 Token 再用一个整数表示，这个整数就叫 **Token ID**。

比如输入“人工智能很有趣”，某个分词器可能把它切成“人工”“智能”“很”“有趣”，另一个分词器可能切得更细。具体切法不能光靠文字猜，要用对应模型的分词器看。词表中的 Token ID 只是标识符，编号 120 比编号 100 大，并不表示它的语义也“大一点”。

模型会根据 Token ID 在一张参数表里取出向量，这一步叫 **Embedding（嵌入）**。可以把它想成把离散的符号映射成一组可参与数学运算的数字。例如词表里某个 Token 对应一个 4096 维向量，那么模型接下来主要处理的就是这些向量，而不是字符串。

这张 Embedding 表可以理解为一个很大的二维数组。假设词表有 50,000 个 Token，每个向量有 4,096 个数，那么它的形状就是 `[50000, 4096]`。输入里出现 Token ID 1234，程序就取出第 1234 行。这里的向量是训练得到的参数，里面每一个数都经过模型学习，并不是人事先给“人工智能”写好的解释。后面的 Transformer 会继续改变这组向量，让它带上当前句子的上下文。

一条消息的输入里通常还会有系统提示词、历史对话和模型要求的特殊控制 Token。对于聊天模型，服务端还要依照模型的 **Chat Template（对话模板）** 把角色和内容拼成它熟悉的格式。同样一句用户提问，前面多了一万字历史聊天记录，最终送进模型的序列就可能长很多。等待第一个字的时间往往也会被拉长。

### Transformer 是怎样利用上下文的

常见的大语言模型以 **Transformer** 为基础。它由多层重复的结构堆叠而成，每一层都在加工上一层传来的向量。

其中最有特点的是 **Attention（注意力）**。假设句子是“我把水杯放在桌上，它差点掉了”，模型处理“它”时，得根据上下文判断这个代词指什么。注意力提供了一套按相关性汇总前文信息的计算办法。

每个位置的向量经过几组线性变换，会得到 **Q（Query，查询）**、**K（Key，键）** 和 **V（Value，值）**。可以把 Q 看成“我现在想找什么信息”，K 是各个位置提供的“匹配线索”，V 是真正要汇总过来的内容。当前位置的 Q 与前文的 K 计算匹配分数，分数经过 Softmax 变成权重，然后用权重对各个 V 加权求和。

数学上常写成：

$$
\operatorname{Attention}(Q,K,V)
=\operatorname{softmax}\left(\frac{QK^\mathsf{T}}{\sqrt{d_k}}+M\right)V
$$

公式可以用三个词的位置来读。假设当前位置的 Q 分别与三个 K 算出分数 `1、2、3`，Softmax 会先对分数取指数，再除以指数之和，得到大约 `0.09、0.24、0.67`。最后让三个 V 分别乘上这三个权重并相加。第三个位置提供的信息占比最大，但另外两个位置也参与了输出。这里的 Q、K、V 都是向量；实际分数来自向量点积，公式里的 `√dₖ` 用来缩放分数，避免维度增加时数值过大、Softmax 过早变得尖锐。

所以，Attention 真正完成的是一次**按当前需要，从可见位置汇总信息**的操作。前面用“它指代哪个词”举例只是帮助理解；在模型里，注意力头处理的是向量之间的关系，也可能关注句法、位置、数字或更抽象的模式。

这里的 $d_k$ 是每个注意力头中 K 的维度，$M$ 是遮罩项。对因果语言模型，遮罩会把未来位置挡住，这就是 **Causal Mask（因果遮罩）**。例如模型正在预测第六个 Token，第六个位置可以看见自己和前五个位置，不能看见第七个位置。这保证了训练时已经摆在那里的未来 Token 不会提前泄露给当前位置。

模型通常会把注意力拆成多个 **Head（头）**，每个头用自己的投影学习不同的信息关系，这就是 **MHA（Multi-Head Attention，多头注意力）**。注意力层之后还有一段逐位置处理向量的 **FFN（Feed-Forward Network，前馈网络）**，常由 **MLP（多层感知机）** 实现。中间还穿插 **Residual Connection（残差连接）** 和 **LayerNorm / RMSNorm（归一化）**，让深层网络更容易训练。词序信息则可以通过 **RoPE（旋转位置编码）** 融入 Q、K，帮助模型区分“我昨天见到他”和“他昨天见到我”。

一层 Transformer 里，这几个部件各有自己的工作。多头注意力负责让当前位置读取上下文；FFN 负责对已经汇总好的向量进一步做非线性变换，可以想成每个 Token 都经过同一套“小网络”；残差连接会把进入子层前的向量加回输出，让信息和梯度更容易穿过很多层；归一化则调整向量的数值尺度，使深层训练更稳定。它们在同一层里分工不同。

位置编码的作用还可以再往下看一层。仅靠 Q 和 K 的内容，注意力并不能天然知道两个 Token 相隔多远。RoPE 将向量的某些维度按位置进行旋转，位置不同，旋转角度也不同。Q 和 K 做点积时，这种旋转关系就会影响匹配分数，因此模型能利用相对位置信息。它也解释了后面 MLA 为什么需要专门处理位置编码：位置相关的 K 不能随意和不带位置信息的压缩表示混在一起。

经过多层 Transformer，模型拿到末尾位置的表示，通过 **LM Head（语言模型输出头）** 计算词表里每个 Token 的分数。这些原始分数叫 **Logits**。再由采样策略决定下一步选哪个 Token。

如果每次都选分数最高的候选，叫 **Greedy Decoding（贪心解码）**；用 **Temperature（温度）** 调节分布，配合 **Top-k** 或 **Top-p** 限制候选范围，就能在合理范围内增加回答的变化。Top-k 留下概率最高的 k 个候选，Top-p 保留累计概率达到阈值的一组候选。选出来的 Token ID 最后经过 **Detokenization（反分词）** 才变成屏幕上的文字。

举个很小的例子，假设四个候选 Token 的概率是 `0.50、0.30、0.15、0.05`。使用 Top-k=2，就只从前两个候选里采样；使用 Top-p=0.8，就按概率从高到低保留累计达到 0.8 的前两个，再重新归一化进行采样。Temperature 作用在分数分布上，温度降低通常会让高概率候选更突出，温度升高则让分布更平缓。它们控制的是**如何选 Token**，不改变 Transformer 这一轮已经算出的隐藏表示。

生成的 Token 会被接回输入，模型继续预测下一个，这个过程会反复进行。

## 3. 为什么处理输入和生成输出是两种工作？

对同一个模型，处理已经输入的文本与逐字生成答案，计算负担相差很大。

假设一位用户上传了 4000 个 Token 的材料，要求模型总结。模型需要先把整段输入送过 Transformer。因果遮罩会保证每个位置只利用它前面的信息，但这 4000 个输入位置可以在同一次前向计算中并行处理。这段工作叫 **Prefill（预填充）**。

完成 Prefill 后，模型已经拥有输入序列各层的上下文状态，并且可以根据末尾位置的 Logits 选出第一个新 Token。随后进入 **Decode（逐步解码）**：把刚生成的 Token 送进模型，预测下一个，再送进去，再预测下一个。通常的一步 Decode 只向前推进一个生成位置。

```text
输入：4000 个 Token
       └──── Prefill：处理已有的 4000 个位置 ────┐
                                                  ▼
                                              第 1 个输出
                                                  │
                                             Decode 第 1 轮
                                                  ▼
                                              第 2 个输出
                                                  │
                                             Decode 第 2 轮
                                                  ▼
                                              第 3 个输出……
```

如果模型生成了 300 个 Token，那么 Prefill 可能只做了一段大规模计算，后面却需要接连执行许多轮 Decode。输入长短主要影响开始回答前的处理工作；输出长短会影响后面要跑多少轮。

容易弄混的一点是：**第一个输出 Token 通常在 Prefill 结束时就能选出来**。举个小例子，输入为 `[A, B, C, D]`，Prefill 处理四个位置，取得末尾 D 的预测分数，采样出 E；接下来第一次 Decode 把 E 当作新位置送入模型，并预测 F。之后再输入 F，预测 G。每轮只需要计算新增位置的各层表示，历史注意力状态会由缓存提供。

为什么说 Prefill 更容易发挥大矩阵计算的优势？因为它有很多输入位置可以一起计算，模型权重读到设备上以后，能被同一批位置反复使用。Decode 单轮要处理的新位置少，尤其在低并发时，可能花不少时间一遍遍读取模型权重和历史缓存。于是经常出现一种典型情况：**Prefill 更容易受计算能力影响，而低并发 Decode 更容易受内存带宽影响。** 当并发、序列长度和硬件变化时，瓶颈也会跟着变。

### 每轮都要重算历史记录，代价太高了

接着想一个更具体的问题。模型刚处理完 4000 个输入 Token，现在生成了第一个输出。如果第二轮仍然把前面 4001 个位置完整地重新计算，第三轮再把 4002 个位置全部重算，越往后重复工作越多。

自回归 Transformer 的因果遮罩给了我们一个简洁的办法：过去位置算出的 K 和 V 不会因为后面又增加了 Token 而改变，因此可以把它们保存起来。保存下来的内容叫 **KV Cache（键值缓存）**。

下一轮只计算新位置自己的 Q、K、V，然后拿新的 Q 去读取已经缓存的历史 K、V。历史位置的大量投影计算就省掉了。KV Cache 主要保存的是每层注意力需要的键值状态，并非整层全部中间激活，也不是把模型的所有结果直接复制下来。

沿着刚才的 `[A, B, C, D] → E → F` 来看，Prefill 会把 A 到 D 在**每一层**产生的 K、V 保存下来。计算 E 时，各层只生成 E 的新 K、V；当前层的 Q_E 与缓存中的 K_A、K_B、K_C、K_D 以及 K_E 匹配，再对对应的 V 加权求和。进入下一层时，又使用下一层自己的那一份 KV Cache。也就是说，缓存并不是整段对话共用的一张表，而是每层各有对应的历史键值。

缓存省掉的是历史 Token 在 Transformer 各层重新前向的一大部分工作，**并没有省掉新 Token 对历史 K、V 的注意力读取**。这也是为什么对话越长，即使每轮只输入一个新 Token，Decode 仍然可能逐渐变慢：计算新位置时要查看的历史缓存越来越长。

节省计算必然要付出储存空间。按常见多头或分组查询注意力模型的布局，一个 Token 的 KV Cache 原始大小可以估算为：

$$
\text{KV 字节数/Token}
=2\times L\times H_{kv}\times D\times B
$$

其中 $L$ 是 Transformer 层数，$H_{kv}$ 是每层的 KV 头数，$D$ 是单头维度，$B$ 是每个元素的字节数。前面的 2 表示 K 和 V 各保存一份。

以 Llama 3.1 8B 的一种常见 BF16 部署配置为例：32 层、8 个 KV 头、每头 128 维，每个 BF16 元素 2 字节。算下来，一个 Token 的 KV Cache 是：

$$
2\times32\times8\times128\times2
=131072\ \text{字节}=128\ \text{KiB}
$$

一条 8192 Token 的长对话，原始 KV Cache 就约 1 GiB。要是 12 条这种长对话同时生成，光历史键值数据就会占去约 12 GiB，还没有算模型权重、缓存块尾部的余量以及其他运行开销。

这个数字还可以解释一种很常见的现象：同样是 12 个用户，如果每人只有 512 Token 的上下文，缓存压力远小于每人 8192 Token。只监控“当前有多少条请求”是不够的，调度器需要知道**每条请求已经占了多少 Token，以及接下来还可能增长多少**。因此 KV Cache 往往决定了一个推理实例能同时承载多少条长会话。

于是服务系统遇到了新的瓶颈：GPU 算力也许还够，但显存已经快被这些不断增长的聊天记录塞满了。

## 4. 聊天越聊越长，显存怎么分才不浪费？

一位用户的对话可能只生成 20 个 Token，另一位用户可能继续写出 2000 个。服务器在请求开始时很难知道它最终会用多少 KV Cache。

最省事的做法是给每条请求预留一大段连续显存，比如按允许的最大上下文长度先留够空间。这样实现简单，代价却很明显：短请求用不了那么多，剩余的空间被预留着；几条长短不一的请求结束后，显存中还可能出现零零散散的空洞。外面看着有空闲空间，新请求却未必能找到合适的一整段。

这和操作系统早期管理内存时碰到的问题很像。vLLM 的 **PagedAttention** 借鉴了分页管理的思路：把 KV Cache 按固定大小拆成 **Block（块）**，每条请求维护一张 **Block Table（块表）**。模型看到的 Token 顺序是连续的，块在显存里的实际位置可以是分散的。

假设每块能容纳 16 个 Token。请求 A 已经产生 34 个 Token 的上下文，它需要三个块：前两个装满 32 个位置，第三个只用了 2 个位置。A 继续生成到第 48 个 Token 时，第三块刚好装满；再生成第 49 个 Token，就需要从空闲池里申请第四块。

```text
请求 A 的逻辑块： [A0] → [A1] → [A2] → [A3] ……
                       │      │      │
块表记录的物理块：      P7     P2     P9

GPU 显存中：    [P0 空闲] [P1 其他请求] [P2 A1] ... [P7 A0] ... [P9 A2]
```

真正读取注意力时，内核根据块表定位各个物理块，按序取到历史 K、V。这样能把原来浪费在过度预留和碎片上的空间省下来，让更多请求进入同一个服务实例。每个块尾部仍可能留有少量空位，但浪费被控制在块的粒度附近。

再算一次空间账。块大小为 16，A 用了 34 个 Token，会占 3 块，实际有 48 个位置，尾部空了 14 个。A 再生成 14 个 Token 前，不需要申请新块；到第 49 个 Token 才申请第 4 块。系统可以把别的请求分到其他空闲块，不必替 A 提前留出几千个位置。

这里有两个“块”容易混淆：**逻辑块**是请求视角下按 Token 顺序编号的第 0、1、2 块；**物理块**是 GPU 显存中实际被分配的存储位置。块表存放两者的映射。真正执行注意力的 Kernel 需要理解这套映射，因此 PagedAttention 既涉及缓存分配器，也涉及如何读取缓存的内核实现。

**PagedAttention 改善了缓存布局和空间利用率。** 历史 KV 的实际数据量依旧随上下文增长。要继续压缩这部分占用，还可以从模型架构本身动手。

### 一层注意力，为什么不一定要存同样多的 K 和 V？

前面讲过 MHA：多个 Query Head 各自有对应的 Key Head 和 Value Head。如果把 32 个查询头全部配上独立的 KV 头，每个 Token 要存的 K、V 就很多。

**GQA（Grouped-Query Attention，分组查询注意力）** 让一组查询头共用一组 K、V。例如 32 个查询头分成 8 组，只保存 8 组 KV 头，同样的层数和头维度下，缓存量会降到原来四分之一。**MQA（Multi-Query Attention，多查询注意力）** 更进一步，所有 Query Head 共用一组 K、V。具体共享到什么程度，需要结合模型效果与硬件效率来选。

可以把同一层的 32 个 Q 头排成四排，每排八个。MHA 要为每个 Q 头各存一组历史 K、V，总共 32 组；GQA 如果每四个 Q 头共享一组，就只存 8 组；MQA 则只存 1 组。模型仍可以保留 32 个不同的 Q 头去提问，只是供它们查阅的历史键值被共享了。这样节省的是**每个 Token、每一层的缓存尺寸**，对长上下文和多并发特别重要。

共享的代价是不同查询头能读取的 KV 表示种类减少，模型训练时需要学会利用这种结构。也正因为它改变了注意力层权重的形状，通常要在模型架构和训练阶段就确定，不能只在部署时把一个普通 MHA 模型的 KV 随意合并。

有些模型采取了另一条路。**MLA（Multi-Head Latent Attention，多头潜在注意力）** 用低秩联合压缩，把 K、V 的信息压到较小的潜在表示里。推理时主要保存压缩后的 KV 潜变量以及需要的位置信息，而不再缓存每个头展开后的完整 K、V。DeepSeek-V2 等模型采用了这一路线，并使用相应的位置编码设计来处理压缩与 RoPE 的配合问题。

假设原本每个 Token 在一层需要保存很多组高维 K 和 V，MLA 会先从输入向量算出一个较短的 **KV Latent（KV 潜在向量）**。它相当于一份压缩过的共同信息；各注意力头需要的 K、V 可以通过不同的投影从中得到。真正优化过的实现还会把一些投影计算合并到 Q 或输出侧，避免每轮都把完整 K、V 重新展开并缓存。

RoPE 让 K 的一部分信息依赖 Token 位置，直接压缩、再任意合并矩阵会破坏这种位置关系。因此 DeepSeek-V2 的 MLA 把位置相关的分量单独安排，并使用解耦的 RoPE 设计。读论文时看到 **low-rank compression（低秩压缩）**、**latent KV**、**decoupled RoPE（解耦旋转位置编码）**，说的就是这套配合。这些设计最终让每个新 Token 在显存里留下的历史状态更小，注意力计算也会相应改写以使用压缩表示。

GQA 主要在“多个查询头共享多少组 KV”上做文章；MLA 更进一步改变了“把什么表示保存到缓存里”。PagedAttention 对已经生成的缓存进行管理，GQA 和 MLA 则影响模型每生成一个 Token 要保存哪些数据。

### 如果十个人问的开头完全一样呢？

假设公司有一个内部问答机器人。每位员工提问前，系统都会附上一段相同的 2000 Token 规章制度。如果十个人连续提问，服务器每次都从头计算这段共同前缀，显然重复了很多工作。

**Prefix Caching（前缀缓存）** 就是让相同前缀已经算过的 KV 能被后续请求复用。请求 A 用过某段固定提示词，B 又发来了同样的前缀，系统可以检查缓存块对应的 Token 内容及其他必要上下文是否匹配，命中后直接复用那部分 KV，接着只处理 B 自己新增的内容。

缓存是否命中，还受分词结果、模型版本、位置、注意力语义以及系统实现的缓存规则约束。对用户来说，“两条问题都在谈报销”这种语义相似还不够；能复用的通常是**真正相同且上下文条件一致的前缀计算**。大量重复系统提示词、模板和固定材料时，这项优化就很有价值。

比如固定系统提示词是 1024 个 Token，A 输入“报销期限是多少”，B 输入“出差补贴怎么算”。若两条请求送入模型的前 1024 个 Token 完全一致，而且缓存仍在，B 就可能直接继承前 1024 个位置算好的 KV，再从自己的问题开始继续 Prefill。若 B 只改了系统提示词中的一个 Token，命中范围就可能在那个位置之前结束。前缀缓存常与块级 KV 管理结合，很多实现以完整缓存块为单位复用，因此前缀相同的长度、块大小和缓存生命周期也会影响收益。

经过这几步，显存利用率上来了，计算也少了。但一个服务始终还有另一个难题：请求是随时到达的，长短不一，怎样让 GPU 尽量持续工作？

## 5. 一张 GPU 同时回答很多人，谁该先执行？

假设 A、B、C 三位用户已经在生成回答。它们每人都只需要再生成一个 Token，就能进入下一轮。此时 D 带着一篇很长的文章来到服务器，等待处理输入。

最朴素的方式是 **Static Batching（静态批处理）**：凑齐一批请求，所有请求一起执行，等这一批完成再接下一批。这适合形状整齐的任务，但在线聊天会出现短请求提前结束、长请求拖住整批的问题。

**Continuous Batching（连续批处理）** 更适合自回归生成。引擎在每轮迭代（Iteration）重新决定活跃请求集合：A 结束了就释放它占用的缓存和执行位置，新来的 D 如果资源允许就进入下一轮，B、C 继续 Decode。这样一批请求不必从头到尾绑定在一起。

假设现在 A 和 B 正在生成，A 只剩 1 个 Token 就结束，B 还需要 100 个。静态批处理中，如果同一批的生命周期被绑定，A 结束后留下的位置可能要等 B 完成才能给下个请求。连续批处理在 A 结束后，就能把 C 纳入后续迭代。这里“批”指的是**这一轮一起送进模型的工作**，并不是把多个用户的文本拼成同一段话；每条请求仍有自己的 Token 序列、采样状态和 KV Cache。

调度器每轮挑选请求，构造本轮要处理的 Token 和对应的缓存映射，再交给模型执行。一次 GPU 前向可以含有多条请求的 Decode Token，也可以按照引擎的调度策略混入一部分 Prefill Token。服务高并发时，大模型权重由更多 Token 共同使用，GPU 的利用效率就可能比单用户推理高得多。

```
时间往右走 →

轮次 1： A(Decode)  B(Decode)  C(Decode)
轮次 2： A(完成)    B(Decode)  C(Decode)  D(Prefill)
轮次 3：            B(Decode)  C(完成)    D(继续 Prefill)
轮次 4：            B(Decode)             D(Decode)
```

这个调度器除了看请求数量，也要看 **Token Budget（Token 计算预算）** 和 KV Cache 的剩余块数。引擎中的 `max_num_seqs` 一类参数限制同时安排多少条序列，`max_num_batched_tokens` 一类参数限制某轮可处理多少 Token。不同框架与版本对这些参数的默认值和调度优先级可能不同，但资源约束始终是核心。

### 长文章一进来，正在生成的回答卡住了

现在 D 的文章不是几百个 Token，而是两万个。一次 Prefill 需要做相当多计算。假如调度器直接安排这个长 Prefill，正在 Decode 的 B 和 C 可能要等它完成大段计算后，才有机会继续吐下一个 Token。于是 B 的回复忽快忽慢。

**Chunked Prefill（分块预填充）** 把长输入拆成多段，分多轮处理。比如当前迭代预算为 2048 Token，B 和 C 各需要处理一个 Decode Token，那么引擎可以把剩余预算的一部分交给 D 的一段 Prefill。下一轮继续为 D 安排下一段，也让 B、C 有机会持续生成。

把数字代进去更清楚：某轮最多允许处理 2048 个 Token，B、C 各占 1 个位置，还剩 2046 个名额。D 有 10,000 个尚未处理的输入 Token，这轮先处理其中 2046 个，保存这部分位置产生的 KV；下一轮继续处理后面的输入位置。D 的 Prefill 不是每一块都从头重算，后续块会利用前面块已经建立的上下文状态。这样 B、C 可以穿插执行 Decode，D 也能逐步完成长输入。

因此 Chunked Prefill 有两个作用：它让长输入的工作可以分批安排，还让调度器能在 Prefill 和 Decode 之间分配每轮预算。块大小越小，调度越灵活，但可能牺牲大矩阵计算效率；块太大又容易让已经在生成的请求等得久。

```text
D 的长输入： [第 1 段] [第 2 段] [第 3 段] ...

某一轮：B、C 执行 Decode + D 计算一段 Prefill
下一轮：B、C 继续 Decode + D 继续处理下一段
```

分块长度、请求优先级和迭代预算会影响两种任务怎样交错。块设得很大，Decode 可能遇到较长的停顿；块设得太小，Prefill 的大矩阵计算效率和调度成本又可能受影响。工程上通常会同时观察第一个 Token 的等待时间、Token 之间的延迟和总吞吐量。

**Preemption（抢占）** 是另一个调度问题：活跃请求占满资源，调度器为了给更紧急的请求腾位置，有时会暂停某个请求，甚至回收其缓存并在恢复时重算部分内容。抢占次数多，表面上请求能被接纳，实际做的重复工作也可能增多。

### Prefill 和 Decode 直接交给不同的机器

对于规模更大的服务，还有一种做法叫 **PD 分离（Prefill/Decode Disaggregation，预填充与解码分离部署）**。

一组 GPU 主要负责 Prefill，另一组 GPU 主要负责 Decode。输入先到 Prefill 节点完成上下文计算，然后把生成的 KV Cache 传给 Decode 节点，后者接着逐 Token 生成。系统因此可以分别给两类负载配置资源：Prefill 侧侧重大吞吐的输入处理，Decode 侧侧重稳定的逐 Token 延迟。

不过跨节点传输 KV Cache 需要时间，也要消耗网络带宽。采用什么连接器、怎样搬运缓存、把多少请求放到两侧，都需要实测。尤其是短输入、短输出场景，额外的数据传输可能抵消收益。PD 分离最直观的价值是**让两种差异很大的负载可以分别扩容和调优，并降低长 Prefill 对 Decode 尾延迟的干扰**。

前面用 Llama 3.1 8B 估算过，一条 8192 Token 上下文的原始 KV 约 1 GiB。如果 Prefill 和 Decode 放在不同 GPU 上，就得考虑这份状态怎么传输：走机内 **NVLink**（过去多GPU之间的通信主要依靠通用的**PCIe**总线，但PCIe传输速度较慢且延迟较高。NVLink专为GPU设计，替代了多颗芯片之间的“超级高速公路”）、跨节点 RDMA，还是通过其他传输路径，耗时可能差很多。RDMA 全称为远程直接内存访问，即远程直接内存访问，是一种能够让一台计算机直接读取另一台计算机内存的技术，支持在合适的硬件和软件条件下减少数据搬运时的 CPU 参与；如果设备和网络栈支持，还可以使用面向 GPU 内存的传输路径。传完之后，Decode 侧还要把它接入自己的缓存管理，才能继续生成。PD 分离增加了系统复杂度，换来的是可以分别决定需要多少台机器来处理输入、多少台机器负责持续输出。

到这里，vLLM、SGLang 这样的推理引擎到底在忙什么就比较清楚了：它们围绕模型的前向计算，处理请求调度、批处理、缓存、执行以及输出。下一层还有 CUDA 内核、矩阵运算库和具体 GPU 硬件负责真正把计算跑完。

## 6. GPU 为什么适合跑模型？先从一块矩阵说起

大语言模型每一层都要做很多矩阵乘法。比如一个输入张量形状为 `[2048, 4096]`，权重矩阵形状为 `[4096, 4096]`，计算结果形状就是 `[2048, 4096]`。其中的 2048 可以理解为本轮共同处理的多个 Token 位置，4096 是示意的隐藏维度。

矩阵的不同输出元素可以并行计算，每个元素又包含许多乘法与加法。这类工作很适合 GPU 的大规模并行执行。

**CPU** 的核心数量通常相对较少，但是每个核心都非常强。可以做乱序执行、分支预测、复杂指令调度等功能，目的是让单个线程尽可能快。所以 CPU 比较适合控制逻辑复杂、分支较多、任务类型多样的程序，比如操作系统、业务逻辑、数据库和串行程序。

**GPU** 则是面向高吞吐设计的。它拥有大量计算单元SM，每个 SM 内部又包含多种不同类型的计算单元，比如CUDA Core、Tensor Core，一般采用 SIMT 这种执行模型，也就是多个线程执行相同指令但是每个线程处理不同数据，所以特别适合矩阵乘法、图像处理、深度学习这种矩阵计算的任务。GPU 还具有较高的显存带宽，并且会通过大量 warp 并发执行来隐藏访存延迟。

**NPU** 则是在 GPU 基础上进一步针对神经网络计算做专用化。这里不同厂商的 NPU 架构差异比较大，但共同特点是都会重点优化矩阵乘法、卷积这类深度学习计算。因为神经网络里基本都是矩阵乘法、卷积、激活函数等等，本质就是大量的乘加运算，所以 NPU 在硬件上放大量专门做矩阵乘加的计算单元，让这类运算跑得非常高效。

### CUDA 程序到底怎么把工作分给 GPU？

以 NVIDIA GPU 为例，开发者可以用 **CUDA C++** 编写一段 GPU 执行的函数，叫 **Kernel（内核）**。内核启动时，程序会指定一组线程构成的 **Grid（网格）**。Grid 由多个 **Block（线程块）** 组成，一个 Block 又包含很多线程。

硬件把 Block 安排到 **SM（Streaming Multiprocessor，流式多处理器）** 上。SM 内部把线程按 **Warp（线程束）**组织。在 NVIDIA 常见 CUDA 架构中，一个 Warp 是 32 个线程；它们通常协同执行指令，每个线程读写自己的数据。负责普通算术的执行单元常被称作 **CUDA Core**，适合矩阵乘加的还有 **Tensor Core**。

```text
Grid（一次 Kernel 启动）
 ├─ Block 0 ── Warp 0（32 线程）
 │            └ Warp 1（32 线程）
 ├─ Block 1 ── Warp 0（32 线程）
 │            └ Warp 1（32 线程）
 └─ Block 2 ── ...

GPU 上多个 SM 共同执行这些 Block
```

如果某个 Warp 正在等显存数据，SM 可以转去执行另一个已经就绪的 Warp。描述 SM 上实际驻留 Warp 数占硬件最大驻留数比例的指标，叫 **Occupancy（占用率）**。让足够多的 Warp 驻留，有利于隐藏访存或指令延迟。不过当寄存器使用量、线程块大小或共享内存配置变化时，Occupancy 也会跟着变化，最终还得看 Kernel 真正跑得快不快。

拿一个 Block 举例，配置 256 个线程，就能分成 8 个 Warp。SM 能同时放多少个这样的 Block，还受寄存器、共享内存以及硬件线程数上限约束。一个 Kernel 如果给每个线程分配了很多寄存器，SM 上可同时驻留的 Warp 就可能变少；其中一些 Warp 卡在读数据时，调度器能切换的备选 Warp 也变少。

这里还要分清 **Occupancy** 和平时监控里写的 **GPU Utilization（GPU 利用率）**：前者是一个 SM 上驻留 Warp 与硬件上限的比例，后者通常是观察一段时间 GPU 是否忙碌或执行了多少工作。占用率低不必然慢，占用率高也不代表计算单元已经充分发挥性能。

CPU 中常见的 **SIMD（单指令多数据）** 是一条指令并行处理多个数据元素；GPU 的执行机制常用 **SIMT（单指令多线程）** 描述，表现为一个 Warp 中多个线程执行相同指令、各自拥有独立线程状态。两者都在利用数据并行，但抽象方式与硬件调度有所区别。

### GPU 算得很快，为什么还会等数据？

一张 GPU 由计算单元和不同层次的存储共同组成。模型权重通常从 **SSD（固态硬盘）** 加载，经由 CPU 一侧的系统内存（常见 **DDR**），再进入 GPU 设备内存。高性能 GPU 经常使用 **HBM（高带宽内存）**。它的容量决定能放下多少权重、KV Cache 和临时张量；带宽决定这些数据能以多快的速度输送给计算单元。

进入 GPU 以后，数据还会经过不同缓存层次，例如共享于多个 SM 的 **L2 Cache**、靠近各 SM 的 **L1 Cache**、Block 内线程共享的 **Shared Memory（共享内存）**，以及每个线程私有的 **Register（寄存器）**。离计算核心越近的存储通常越快，容量则更受限制。

假设一段计算需要读取 1 GB 的数据，做的算术却只有很少几步。即便 GPU 有极高的理论浮点算力，数据不送到执行单元，算力就用不起来。这叫 **Memory-bound（访存受限）**。如果数据已经送得很快，计算单元仍要花很长时间完成大量矩阵乘加，那更接近 **Compute-bound（计算受限）**。

判断瓶颈时常用的一个思路是 **Roofline Model（屋顶线模型）**。它把性能上限与两个指标联系起来：设备峰值算力，以及显存带宽乘以 **Arithmetic Intensity（计算强度，单位数据搬运对应的运算量）**。算力常以 FLOPS 表示，即每秒能完成多少次浮点运算；带宽常以 GB/s 或 TB/s 表示，即每秒能搬运多少字节。计算强度低时，更容易受带宽限制；计算强度高时，更可能逼近算力上限。

例如只做理论分析，假设一台设备的某种精度峰值算力为 100 TFLOPS，显存带宽为 2 TB/s。如果一个 Kernel 每搬运 1 字节数据只做 10 次浮点运算，那么带宽能够支持的运算速度上限约为 `2 TB/s × 10 FLOP/Byte = 20 TFLOPS`，远低于算力峰值；当计算强度上升到 100 FLOP/Byte，按带宽算的上限为 200 TFLOPS，实际仍受 100 TFLOPS 的计算峰值限制。这个例子说明，优化 Kernel 不能只盯着减少指令，还要看每搬一次数据究竟做了多少计算。

GPU 程序还关心访问方式。一个 Warp 的线程如果读取相邻地址，硬件更容易把访问合并为较少的内存事务，叫 **Coalesced Access（合并访存）**。如果共享内存中的多个线程在同一时刻争用同一个 Bank 的不同地址，可能发生 **Bank Conflict（Bank 冲突）**。这些细节对算子性能影响很大，尤其是在写矩阵乘法或 Reduction（规约）内核时。

比如让 Warp 中 32 个线程各读取一个连续的 4 字节浮点数，它们一共需要 128 字节连续数据，通常比较容易形成高效的访存事务。如果每个线程隔着很大步长读取一个值，硬件可能要发起更多内存事务才能取齐这 32 个数。同样都是“32 次读取”，执行时间就可能差不少。优化矩阵运算时经常先调整线程与数据的对应关系，再考虑更复杂的数学算法。

## 7. 已经有 PyTorch 了，为什么有人还在手写 CUDA 和 Triton？

PyTorch 可以直接写 `C = A @ B`。这行代码调用的是一个矩阵乘法算子，底层需要找到相应的 GPU 实现，把数据准备好，再启动 Kernel。对于常见形状和精度，框架往往能调用高度优化的计算库，比如 **cuBLAS**。卷积以及许多深度学习操作可以利用 **cuDNN**。PyTorch的默认操作（如`torch.add`、、`torch.relu`等`torch.softmax`）在执行时，通常是按操作逐个下发到GPU的。这意味着每做一个简单的算子，GPU从显存（HBM）中把数据读进来，计算完成再写回显存。对于显存带宽确定（Memory-bound）的算子，这会在“倒腾数据”上造成大量的时间浪费。

**cuBLAS、cuDNN、CUTLASS **是什么

​	**cuBLAS** 是 NVIDIA 提供的高性能线性代数库，实现一些基础线性代数操作，比如向量运算、矩阵乘法，尤其是 GEMM。像深度学习里的 Linear、MLP，以及 Attention 里面很多矩阵乘法，底层都可以转化成 GEMM，然后调用 cuBLAS来执行。它的特点是接口比较高层，用户只需要告诉它矩阵的 shape、数据类型、转置方式等，不需要自己写 CUDA kernel，底层会针对不同 GPU 架构选择高度优化的实现。

​	**cuDNN** 则比 cuBLAS 更偏深度学习领域。它提供的是深度学习常见算子的高性能实现，例如 convolution、attention、normalization、activation 等。比如 PyTorch，在执行很多 GPU 算子时，底层可能会调用 cuDNN 或 cuBLAS。

​	**CUTLASS** 则更靠近 **CUDA** **kernel** 实现这一层。它是一个基于 C++ 模板的高性能 CUDA 计算库，主要提供 GEMM、卷积等算子的可组合实现。相比 cuBLAS，CUTLASS 给开发者暴露了更多底层细节，比如 block tiling、warp tiling、register tiling、shared memory、Tensor Core 矩阵乘加 等，所以开发者可以基于 CUTLASS 定制自己的高性能 kernel。

​	所以实际工程中，如果标准算子能够直接由 cuBLAS 或 cuDNN 高效完成，一般优先调用这些成熟库；如果需要做算子融合、特殊数据布局、特殊 shape 优化，或者开发自定义 kernel，就可能进一步使用 CUTLASS。

但模型里有大量不完全相同的运算。矩阵乘法之后可能紧跟一个偏置加法、ReLU 或 SiLU 激活，接着又做归一化。如果每一步都单独启动 Kernel，中间结果就可能反复写回显存又读出来。这时，即使每个算子本身都算得很快，几次显存往返也会拖慢整段计算，所以需要直接手写 CUDA kernel。

**手写CUDA/Triton**的优势就是可以将多个算子融合（Fuse）到内核中。**Kernel Fusion（算子融合）** 的思路很直接：把合适的连续操作放进同一个 Kernel，让中间结果尽可能留在寄存器或片上存储，最后统一写回。把矩阵乘法、偏置和激活放在一起就是常见场景，这样就能减少内核启动和中间数据读写。

例如，把LayerNorm、残差连接（Residual Add）和激活函数写成一个联合Kernel。数据从显存读入一次，在片上高速缓存（SRAM/寄存器）里把步骤所有算完，再写回一个显存，基本上减少显存访存最多，带来近数倍的（比如FlashAttention的核心逻辑）。**算子（Operator）** 是模型里定义的数学工作，**Kernel** 是让 GPU 实际执行这项工作的程序。一个算子可能由多个 Kernel 完成，多个算子也可以由同一个融合 Kernel 完成。

### FlashAttention 为什么特别有名？

注意力公式中有个容易被忽略的中间结果：$QK^\mathsf{T}$。假设序列有 8192 个位置，单个头的分数矩阵就是 `8192 × 8192`，包含约 6710 万个元素。用 FP16 保存，单个矩阵就占约 128 MiB。序列再变长，中间矩阵的大小会按长度平方增长。

朴素实现可能先把整张分数矩阵写进 HBM，接着读出来做 Softmax，再拿结果去乘 V。模型算术的公式很简洁，存储系统却忙着反复搬动大块数据。

**FlashAttention** 改变了这段计算的组织方式。它把 Q、K、V 分块送进片上存储，在处理一个分块的同时更新 Softmax 需要的统计量，逐步累积注意力输出。关键技巧是 **Online Softmax（在线 Softmax）**：后面来了新的分块，依然能用更新后的最大值与归一化系数修正之前的累计结果。这样不必把完整注意力分数矩阵写到 HBM。

难点其实在 Softmax。假设同一个 Q 对三个 K 的分数是 `1、2、3`，但程序先只拿到前两个 `1、2`。如果直接对这两个分数做 Softmax，得到的权重相加是 1；等第三个分数 3 来了，原来的两个权重都得缩小，因为现在要在三个位置之间共同归一化。朴素分块如果把每块单独归一化再相加，结果就错了。

Online Softmax 不需要把所有分数同时保存下来。每处理一块，它维护当前分数的最大值、指数和，以及按同样尺度累积的 V 加权结果；新的一块到来时，先把旧的累计量按新的尺度调整，再合入新的分数和 V。处理完全部块，才做最后的归一化。FlashAttention 因此可以边读一小块 K、V，边更新正确的总输出，把大量中间数据留在片上。

数学上它仍在计算精确注意力（允许正常浮点运算顺序带来的数值差异），优化重点是数据怎样在 HBM 和片上存储之间流动。FlashAttention 与前面讲过的 PagedAttention 因而解决了不同问题：前者着重注意力计算的 IO，后者着重推理期间动态 KV Cache 的分配与访问。实际推理引擎可以把二者的设计结合在不同内核中。

### 写 Kernel 的工具有哪几层？

如果要自己决定每个线程读哪一段数据、怎样同步、何时写回，可以直接用 **CUDA C++**。编译器通常由 **CUDA Toolkit** 提供，程序运行时会通过 **CUDA Runtime** 与驱动交互。GPU 驱动由宿主机环境管理，容器里的 CUDA 程序还需要得到相应的设备访问权限。

**Triton** 是另一种写 GPU Kernel 的方式。它让开发者以块为单位描述向量化的数据加载、计算和存储，很多布局与并行细节由编译器处理。写 Softmax、LayerNorm 或特殊形状的矩阵操作时，它能减少手写底层线程索引的工作。这门编程语言叫 Triton；NVIDIA 另有一个 **Triton Inference Server**，负责部署和管理模型推理服务。

矩阵乘法还经常用到 **CUTLASS**。它提供可组合的高性能 GEMM（通用矩阵乘法）构建模块，支持不同的分块、数据布局、Tensor Core 指令路径以及多种精度格式。它更像一套方便内核开发者定制矩阵计算的积木；cuBLAS 则更像直接调用的成熟计算库。CUTLASS 近年来也发展了 CuTe 等张量布局与 Python DSL 相关能力。

### 计算做完得够快，启动计算也要够快

Decode 会一轮又一轮地运行许多相似的 Kernel。每个小 Kernel 即使只需几微秒，CPU 仍要准备参数、提交命令、调用驱动。Kernel 很小、启动次数又很多时，这些开销会逐渐显眼。

**CUDA Graph** 可以提前把一组 GPU 操作及其依赖关系组织成图，完成捕获和实例化以后，后续重复执行时直接重放。这减少了逐个提交 Kernel 的 CPU 开销。推理框架常在形状稳定、重复执行频繁的 Decode 路径上利用它。

可以想象一次 Decode 需要依次启动几十个 Kernel：归一化、矩阵乘法、注意力、激活等都要从 CPU 一侧不断提交。假设每次提交都有固定开销，生成 500 个 Token 时，这套启动动作就重复了 500 次。CUDA Graph 在准备阶段记录这些 GPU 操作之间的依赖，之后 CPU 只要发起一次 Graph Replay，就能重放整组操作。GPU 真正执行的数学计算并未因此减少，节约的是反复向 GPU 提交任务的开销。

这也解释了为什么推理引擎会关心图捕获时使用的内存地址和张量形状：图里记录的是一套可重放的操作关系，输入数据要放进与图匹配的缓冲区中。批量大小变化很大时，常见策略是准备几个形状档位，再把请求填进相应的执行图。

用 CUDA Graph 时，动态请求长度、批大小、内存地址等因素也要安排妥当。常见做法是为若干固定形状准备可重放的图，把动态数据放进稳定的缓冲区。它改善的是**提交与调度 GPU 工作的开销**，和 FlashAttention 通过减少数据搬运获得收益是两条不同的优化路径。

## 8. 模型太大放不进显存，除了加 GPU 还能做什么？

假设要部署一个 70B 参数的稠密模型。B 是 Billion，70B 就是约 700 亿个参数。用 BF16 保存权重，每个参数占 2 字节，单是权重理论上就需要约 140 GB 的存储空间。再算上 KV Cache、运行时缓冲区和其他开销，一张普通 GPU 很难独自承担。

最直观的办法是增加 GPU；另一个方向是把每个参数存得更紧凑。这就是模型部署里经常讨论的 **Quantization（量化）**。

### 从 BF16 到 INT4，少掉的是哪些字节？

神经网络最初通常用浮点数保存参数。**FP32** 每个元素 32 位，**FP16** 和 **BF16** 每个元素 16 位。BF16 的指数位较多，动态范围接近 FP32，训练大模型时很常见；FP16 的尾数精度和指数范围则有不同的取舍。

如果把权重换成 8 位整数（INT8）或 4 位整数（INT4），理论上的权重存储量可以大幅下降。一个简化的对称量化过程是：先选一个尺度 `scale`，再把浮点数近似映射成整数。

仍用那份 70B 的模型估算：BF16 权重大约 140 GB；若全部权重都能按 INT8 的 1 字节保存，原始权重数据约 70 GB；按 INT4 的半字节保存，约 35 GB。部署时还要加上缩放因子、元数据、可能保留为高精度的层、KV Cache 和工作空间，所以真实占用会高于这里的理论值。量化之所以常用于推理，是因为 Decode 要反复读取权重，减少读入的字节既省显存，也可能省带宽。

$$
q=\operatorname{round}(w/s), \qquad \hat{w}=s\cdot q
$$

比如原来的权重是 0.71875，尺度取 0.1，编码得到整数 7，还原得到 0.7。存储更省了，但原值和还原值之间有误差。实际量化还涉及分组尺度（Group-wise Quantization）、零点（Zero Point）、离群值，以及哪些算子能够直接利用这种格式。分组尺度是让一小组权重共用一个 scale，比整层只用一个尺度更容易适应不同数值范围。零点则是非对称量化中的整数偏移：可以写成 `q = round(w/scale) + zero_point`，还原时再用 `scale × (q - zero_point)`。

因此在真实部署中，我们会区分“权重以 4 bit 存储”和“所有计算都在 4 bit 上完成”。很多 **Weight-only Quantization（仅权重量化）** 方案只把权重压低精度，计算时仍需要配合较高精度的激活，并使用硬件支持的解包、反量化或混合精度计算路径。速度会不会提升，取决于具体 Kernel、批大小和硬件支持。

常见方案里，**GPTQ** 是一种训练后权重量化方法（Post-Training Quantization，PTQ）。它用校准数据估计量化误差对层输出的影响，借助近似二阶信息与逐步误差补偿，尽量在降低位宽时保留模型效果。

**AWQ（Activation-aware Weight Quantization）** 则利用激活分布找出对输出更敏感的权重通道，通过缩放等方式降低这些关键部分的量化误差。它同样常用于低位宽权重量化。二者都要考虑模型结构、校准样本、精度损失及对应硬件上的实现成本。

用一层线性变换来想这件事：输出由很多 `输入激活 × 权重` 相加得到。某个权重的数值并不大，但如果与它相乘的激活经常很大，量化这个权重产生的一点误差就可能被明显放大。AWQ 利用校准数据观察激活，保护对输出更重要的权重通道；GPTQ 更关注怎样根据校准样本和近似二阶信息，在逐步量化权重时补偿误差。前者的切入口是激活敏感性，后者的切入口是量化误差的优化过程。

还要看推理内核究竟支持哪种权重格式。模型文件小了一半，并不意味着生成速度一定翻倍。某些 INT4 Kernel 需要在计算前解包和转换数据；如果批量很大，计算而非权重读取成为瓶颈，压缩存储带来的收益也会变化。

近年还经常看到 **FP8（8 位浮点数）**。它与 INT8 是不同的数值表示方式。常见 FP8 格式有 E4M3 和 E5M2：前者用更多位数表示有效数字，后者给指数留下更多空间，动态范围更大。

为什么需要指数位？因为神经网络里的数字可能有的很小、有的很大。INT8 量化通常依赖 scale 把连续数值映射到一组整数格点；FP8 自身带指数，可以在有限位宽里覆盖不同数量级。E4M3 用 4 位指数、3 位尾数；E5M2 用 5 位指数、2 位尾数，表示范围和精度侧重点不同。实际训练还可能使用按张量或按块的缩放策略，避免数值溢出或舍入误差累积。讨论 FP8 时，最好同时看模型精度、量化尺度和硬件对相应矩阵指令的支持。

把这些格式放到同一条性能链里看就容易理解了：缩小权重，能够减少权重占用，还可能减少 Decode 频繁读取权重带来的带宽开销。但如果计算时缺少高效的量化 Kernel，或者模型质量明显下降，就需要重新评估这种节省是否划算。

### 参数很多，能不能每次只算其中一部分？

还有些大模型总参数量很大，每个 Token 参与运算的参数量却小得多。这通常来自 **MoE（Mixture of Experts，混合专家）** 架构。

在常见的 Transformer 层中，FFN 会对每个 Token 执行类似的一组变换。MoE 则准备多个不同的 FFN“专家”（Expert），再用一个 **Router / Gate（路由器或门控网络）**，为当前 Token 选择其中少量专家，比如 Top-2 或 Top-8。不同 Token 可以被分配给不同专家。某些架构还额外设置所有 Token 都会使用的共享专家（Shared Experts）。

这样模型可以拥有很大的总参数容量，而一次前向只激活一部分专家。代价是路由器要做选择，专家之间可能出现负载不均，分布在不同 GPU 上的专家还需要跨设备通信。

比如某个 MoE 层有 8 个专家，Router 给一个 Token 计算 8 个分数，挑出分数最高的 2 个专家。这个 Token 只进入这两个专家的 FFN，最后再按路由权重组合输出；下一个 Token 可能会选择完全不同的两个专家。这里“只激活 2/8”说的是**该层专家部分**，注意力层、路由器和其他共享模块照常计算，不能简单地把整个模型计算量算成四分之一。

如果一批 Token 里大多数都被送到专家 3，负责专家 3 的 GPU 就会忙得排队，而其他 GPU 比较空。这就是 MoE 工程里常谈的专家负载不均。模型训练时会设计辅助负载均衡或其他路由约束；部署时也可能通过专家并行、复制热点专家或调整调度减轻问题。

当专家分散在多张卡上时，常使用 **EP（Expert Parallelism，专家并行）**。Token 根据路由结果被送到相应专家所在的 GPU，再把专家输出收集回来。这类交换常用 **All-to-All** 集合通信。一个专家突然特别热门，负责它的设备就容易成为瓶颈，因此实际系统还要处理负载均衡、专家副本和通信安排。

到这里，MoE 和前面讲过的 MLA 可以接起来看了：MoE 让一层中只有被路由到的专家参与计算，MLA 则缩小每个 Token 留在显存中的注意力历史状态。一个主要影响 FFN 的计算路径，一个主要影响注意力缓存，两种设计可以出现在同一个模型中。

### 还嫌 Decode 慢？让小模型先猜一段

推理优化还有一种有意思的方法：**Speculative Decoding（投机解码）**。是一种用于加速大语言模型推理阶段的技术，其核心思想类似于计算机CPU中的“分支预测”：做一个轻量快速的小模型“打草稿”，再由庞大的目标大模型进行“批量验证”。在不改变模型输出质量的前提下，显著提升大模型的生成速度（通常可提速 2~4 倍甚至更高）。

大模型在生成文本时是**逐个 Token 串行生成**的（生成一个，再把结果输回去生成下一个）。这种模式受限于**内存带宽**：每次生成 1 个 Token，GPU 都要把庞大的模型参数从显存搬运到计算单元一次，导致 GPU 处于“大部分时间在等数据，小部分时间在计算”的状态（访存密集型）。如果先让一个体积小、运行极快的“**草稿模型**”（Draft Model）。它用极低的计算开销，连续“猜”出接下来可能出现的 K 个 Token。将这 K 个草稿 Token 一次性输入给真正的大模型（Target Model）。大模型通过**一次并行前向传播**，同时检查这批 Token 哪些是对的、哪些是错的。只要猜对了 M 个（M ≤ K），这 M 个 Token 就可以直接批量生效。也就是说，大模型**用一次计算的时间，办成了过去需要计算 M 次的事**。

比如小模型先猜了“北京是中国的首都”，目标模型在一轮验证中给出每个候选位置的分布，再按规定的接受规则决定能保留多少个。如果前几项通过，便可以一次前进好几个 Token；一旦不通过，就按算法的校正步骤继续生成。

假设草稿模型顺序猜出四个 Token：`北京 / 是 / 中国 / 的`。目标模型在一次前向里可以得到这些候选各位置的预测分布，按相应的验证算法从前往后检查。如果前 3 个都被接受，第 4 个未被接受，那么这轮就可以保留前 3 个，并根据目标分布完成后续校正。相比目标模型每轮只生成 1 个 Token，这种方法有机会用一次较大的验证计算推进多个 Token。

目标模型能并行计算多个候选位置，原因仍然是 Transformer 的因果遮罩：已经给定一整段候选 Token 时，各位置的预测分布可以在同一次前向中算出；真正的生成依赖由接受规则处理。要保持采样分布正确，需要使用与具体投机解码算法匹配的拒绝和修正机制。

不同投机解码算法在接受规则、采样正确性和草稿来源上有所差别。有的用单独小模型，有的在同一模型内加入多 Token 预测头（MTP），还有的利用历史片段提出候选。是否加速取决于草稿命中率、验证成本、批大小与硬件环境。它解决的是生成依赖造成的串行轮数问题，与 CUDA Graph 减少提交开销、KV Cache 减少重复计算各有侧重。

## 9. 一张卡不够时，多张 GPU 怎样合作？

量化之后，模型仍可能需要多张卡。把几张 GPU 放进同一台机器，至少有两种完全不同的使用方法。

第一种：每张卡放一份完整模型。用户 A、B 走第一张卡，C、D 走第二张卡。这是多副本服务，常被看作推理侧的 **DP（Data Parallelism，数据并行）** 或副本并行。它能提高整体服务能力，前提是每张卡都放得下完整模型及自己的缓存。

第二种：两张卡合起来放同一份模型。每张 GPU 只保存一部分权重，共同完成一条请求。这叫 **Model Parallelism（模型并行）**，常见实现包括 TP 和 PP。

**TP（Tensor Parallelism，张量并行）** 把一层里的大矩阵切到多张 GPU 上。例如某层权重矩阵按列切成两半，两张卡各自计算部分输出；后续层根据切分方式，可能需要汇总或交换部分结果。它可以降低每卡权重负担，还能让一层运算跨 GPU 并行，但层与层之间的通信会很频繁。

以矩阵乘法 `Y = XW` 为例，假设 `W` 的形状是 `[4096, 8192]`。两卡做列并行时，每张卡只存 `[4096, 4096]` 的一半权重，两张卡各自算出一半输出列，拼起来才是完整的 Y。某些后续算子可以直接吃各自那一半结果，不必立刻拼接；但如果后续计算要求完整或求和的结果，就得通过 AllGather、AllReduce 等通信把信息交换好。TP 的关键不只是“把矩阵切开”，还要安排**切分后的张量在层与层之间怎么流动**。

**PP（Pipeline Parallelism，流水线并行）** 则按层分工：第一张 GPU 放前半部分 Transformer 层，第二张 GPU 放后半部分层。一个输入先跑完前半部分，再进入后半部分。训练时会把大批数据拆成多个 **Micro-batch（微批次）**，让不同流水线阶段同时忙起来；在线推理也可以组合流水线阶段与不同的调度方式。

比如模型有 32 层，GPU 0 放第 1～16 层，GPU 1 放第 17～32 层。一条请求必须先经过 GPU 0，再把第 16 层输出送到 GPU 1。如果只有这一条请求，前一半计算时 GPU 1 在等，后一半计算时 GPU 0 又可能在等。把工作拆成多个微批次后，GPU 0 在处理下一批时，GPU 1 可以处理上一批，流水线才更容易保持忙碌。流水线刚启动、快结束时的等待常被称为 **Pipeline Bubble（流水线气泡）**。

如果模型层数不多但单层极宽，TP 往往更符合拆分需求；如果模型很深、每张卡可以保存部分完整层，PP 也是一种选择。更大的系统可以让 TP、PP、DP 组合使用，MoE 还会叠加专家并行 EP。长上下文训练或某些特殊推理架构中，还可能使用 **CP（Context Parallelism，上下文并行）**，把序列维度的工作分到不同设备上。

### 几张 GPU 互相通信，也需要时间

同一台服务器里，GPU 可能通过 **PCIe** 或 **NVLink** 连接。跨服务器则可能通过高速以太网或 **InfiniBand** 互联。通信的延迟、带宽和拓扑，会直接决定张量并行和专家并行到底划不划算。

NVIDIA GPU 上常用的通信库是 **NCCL**。它提供多种集合通信操作，训练和推理框架可以用它做 **AllReduce（全规约）**、**AllGather（全收集）**、**ReduceScatter（规约散发）**、**All-to-All（全互换）** 等数据交换。

这几个名字其实描述了数据要怎么走。AllReduce 是先把各卡的数据按元素求和等规约，再把规约结果发回每张卡；AllGather 是每张卡提供自己的一片数据，最后每张卡都拿到拼接后的完整数据；ReduceScatter 则把规约后的结果拆成几片，每张卡只留下自己那一片；All-to-All 是每张卡都把不同的数据片段发给其他卡，比如 MoE 需要把 Token 送到负责不同专家的 GPU。它们是不同的数据交换模式，选择哪一种取决于张量被怎样切分，以及下一步计算需要哪部分结果。

举个训练时的例子：两张卡对同一个参数算出梯度，分别为 2 和 6。数据并行训练通常需要得到一致的平均梯度，于是两边通信，合并为 8，再除以 2，得到 4。两张卡再用这个梯度更新自己的参数，模型副本才能保持一致。

如果模型已经分到很多张 GPU 上，一次前向可能伴随多次通信。随着 GPU 数量增长，计算变快了，通信却可能越来越显眼。这也是为什么集群优化既要看 GPU 算力，也要看卡间拓扑、网络拥塞和集合通信效率。

除了 NVIDIA 的 CUDA 生态，AMD GPU 常见 **ROCm**，华为昇腾加速器则有 **CANN** 等配套软件。

## 10. 这些权重最开始是怎么训练出来的？

前面一直在讲模型如何回答问题。现在把时间拨回模型上线以前。

假设我们希望模型能够预测一句话的下一个 Token。训练数据里有一段“今天的天气很”，正确的下一个 Token 对应“好”。模型第一次可能给“冷”很高的概率、给“好”很低的概率。训练程序会根据预测分布和正确答案计算 **Loss（损失）**，例如语言模型常见的交叉熵损失。

接着发生三件事。第一步是 **Forward（前向计算）**，把输入通过各层网络得到预测；第二步是 **Backward（反向传播）**，对损失求各个参数的 **Gradient（梯度）**；第三步由优化器根据梯度调整参数。反复执行许多轮后，模型权重才逐渐学到数据中的统计规律。

**PyTorch** 中 Tensor 表示多维数据，计算图记录运算之间的依赖，**Autograd（自动求导）** 根据这些关系计算梯度。`loss.backward()` 是一个典型入口。**SGD（随机梯度下降）** 是基础的梯度优化方法；实际大模型训练中，**Adam / AdamW** 等带动量与自适应学习率的优化器更常见。

为了感受梯度到底干了什么，可以把模型缩成一个参数 `w`，预测 `y = wx`。假设 `x = 2`、正确答案是 `6`、初始 `w = 2`，模型预测就只有 `4`。选平方误差 `L = (y-6)²/2`，此时损失是 `2`，对 `w` 的梯度是 `(wx-6)×x = -4`。如果学习率设为 0.1，最简单的梯度下降会更新成 `w = 2 - 0.1×(-4) = 2.4`。下一次预测变成 `4.8`，离答案 6 更近了。真正的大模型把这个过程扩展到数十亿个参数，Autograd 负责沿计算图求出各参数的梯度。

训练过程还要控制 **Learning Rate（学习率）**、Batch Size、梯度累积、权重衰减等参数。Batch 很大时，训练程序可能把它拆成多个 Micro-batch，分别算梯度再累计，最后完成一次优化器更新。

模型初期通常通过大规模数据做 **Pretraining（预训练）**。如果还想让它学会特定的问答格式、指令遵循或行业任务，可以继续用示范数据做 **SFT（Supervised Fine-Tuning，监督微调）**。在一些资源受限的场景里，还会使用 **LoRA（低秩适配）**：在训练时，把原本庞大的预训练模型参数（权重）全部“锁死”不作修改，从而完整保留模型原有的通用能力。在模型的关键层旁边，并联注入一小部分可训练的“低秩矩阵”（通常只占原模型参数的 1% 甚至更低）。训练时只更新这小部分参数。推理时，可以将小矩阵与原模型权重合并，不会增加额外的计算延迟。这样基础大模型可以保持不变，你可以像加载“外挂插件”一样，随时切换、叠加不同的 LoRA 来实现不同的风格或任务。同时 因为冻结了原模型，不会破坏它原本的知识，能有效避免“灾难性遗忘”。

比如一层原本有个 `4096 × 4096` 的权重矩阵 W，包含约 1680 万个参数。LoRA 不直接更新整张 W，而是在它旁边训练两个更窄的矩阵 A、B，使新计算相当于 `W + AB`。如果低秩维度 r 取 16，A、B 的参数总数是 `4096×16 + 16×4096 = 131072`，只相当于原矩阵约 0.78% 的参数量。这里的“低秩”就是用一条窄的中间通道表示权重更新。基础权重仍需参与前向计算，因此 LoRA 主要节省的是需要训练的参数、梯度和优化器状态。

训练结束后一般还要评估。光在训练样本上预测得准，并不代表它能处理真实用户的问题。评测需要准备独立样本，检查准确性、稳定性、特定任务表现。正式部署时如果做了量化、转换模型格式或更换推理后端，部署产物也要重新验证。

### 为什么训练比推理更占显存？

同一个模型，训练时除了权重，还可能要保存梯度、优化器状态以及反向传播需要的中间激活。推理阶段通常只执行前向计算，这些训练状态就不需要长期保留。

当一张 GPU 容纳不了完整训练状态时，可以像前面说的那样进行 DP、TP、PP。训练领域还经常提到 **FSDP（Fully Sharded Data Parallel，全分片数据并行）**：把参数、梯度和优化器状态分片存到多个设备上，在需要某段参数时临时通信取用。**ZeRO（Zero Redundancy Optimizer）** 也围绕减少数据并行训练中的冗余状态展开，按不同阶段选择分片哪些状态。

用两张卡举例：普通数据并行时，两张卡都保存完整权重与训练状态，各自读不同数据再同步梯度；FSDP 则可以让每张卡长期只保留部分参数与训练状态。某一层即将前向时，必要的参数通过 AllGather 临时聚合；这层算完后，可以释放临时聚合的完整参数，反向时再按需要重建并把梯度规约到对应分片。这样省下大量显存，代价是更多通信与状态管理。

ZeRO 常按分片范围谈 Stage 1、2、3：从只分片优化器状态，逐步扩展到梯度和参数。FSDP 与 ZeRO Stage 3 在减少模型状态冗余上有相近目标，具体运行机制和软件接口并不完全相同。

**DeepSpeed** 和 **Megatron-LM** 是常见的大模型训练技术栈。DeepSpeed 提供分布式训练、内存管理和优化器状态分片等能力；Megatron-LM 长期专注于大模型并行训练，提供 TP、PP 等并行技术的工程实现。它们通常和 PyTorch 及底层通信库一起使用。

一次训练可能持续几天甚至更长。机器故障、进程中断、网络异常都可能让任务停下来，所以系统会定期保存 **Checkpoint（检查点）**。一份可恢复训练的检查点通常包含模型权重，还可能包含优化器状态、学习率调度状态、随机数状态和训练进度。恢复时要让这些信息对应起来，才有机会从上次保存的位置继续。

训练数据从 SSD 或网络存储进来，还需要 CPU 做读取、解码、预处理，然后传到 GPU。如果数据加载器跟不上，显卡就会空转；如果多 GPU 同步梯度占了太多时间，增加显卡也未必带来预期的加速。因此从数据读取到参数更新的整条训练流水线，同样属于 AI Infra 的工作范围。

## 11. 模型已经训练好，怎样真正变成一个稳定的在线服务？

训练团队把模型交给部署团队时，交付物远不止一个 `.safetensors` 或其他格式的权重文件。服务启动还需要知道模型的网络结构、隐藏层维度、分词器、对话模板、精度格式，以及哪一套代码能正确执行这些参数。

实际工作中，模型可能先进入一个版本管理系统或 **Model Registry（模型注册表）**。新版本加载之前先做离线评测，确认格式、权重、分词器和计算逻辑一致；再启动一组候选服务，检查模型能否正常加载、输出是否正确、速度是否达到预期。

### vLLM、SGLang、TensorRT-LLM 是什么关系？

你在研究或者训练模型时，可能直接用 Hugging Face **Transformers** 和 PyTorch 调用 `model.generate()`。这在实验阶段很好用。用户数量增加以后，请求调度、批处理和缓存管理就需要更专门的实现。

**vLLM** 是面向大模型推理与服务的引擎，重点包括动态 KV Cache 管理、连续批处理、模型执行和服务接口。**SGLang** 也是大模型推理与服务框架，除了高效运行模型，还提供与结构化生成、程序化推理过程有关的能力。**TensorRT-LLM** 是 NVIDIA 的推理优化与部署技术栈，能够结合其 GPU 架构、高性能 Kernel 和执行优化构建推理服务。

这些框架都位于 API 和 GPU 计算之间：上层接收请求，下层调用模型执行与 GPU Kernel，中间负责调度、批处理和缓存。区别更多体现在模型支持范围、接口、编译与执行优化路径、缓存调度策略以及与硬件的适配程度。比如同一份模型，换一个引擎之后，首 Token 延迟和高并发时的吞吐可能都发生变化。比较这些引擎时，最好统一模型版本、量化精度、输入输出长度分布和 GPU 数量，再观察结果。

**TGI（Text Generation Inference）** 是 Hugging Face 推出的文本生成服务框架，提供流式输出、批处理、量化等功能。Hugging Face 已将 TGI 转为维护模式，对于新部署更推荐 vLLM 或 SGLang 等引擎。**LMDeploy** 则提供大模型及视觉语言模型的压缩、部署和服务能力，包含以 C++/CUDA 实现为主的 TurboMind 引擎，以及 PyTorch 引擎。

选择推理引擎时，最好在目标 GPU 上使用同一模型跑对照测试，分别观察长短输入、不同并发和精度格式下的性能。还有一个容易混淆的名字：**NVIDIA Triton Inference Server** 是模型服务平台，负责接入、管理和调度多种推理后端；前面用于编写 GPU Kernel 的 Triton 则是一门编程语言。

### Docker 负责打包，Kubernetes 负责管理服务

把推理程序部署到线上时，通常要处理 Python 包、CUDA 运行库、模型文件、环境变量和服务配置。**Docker** 容器把应用与所需依赖封装成可重复部署的环境，但 GPU 驱动通常仍由宿主机提供，容器要通过相应运行时获得设备访问权限。

一个服务从单台机器变成许多台机器以后，又会出现新的问题：程序应该启动在哪个节点？某台机器故障怎么办？如果访问量突然增加，要不要多开几个副本？

**Kubernetes（K8s）** 是常见的集群编排系统。它把容器应用部署到 **Pod**，根据资源请求与调度约束把 Pod 放到合适的 **Node（节点）** 上。**Deployment** 可以管理副本数与版本更新，**Service** 为访问这些副本提供稳定入口；GPU 工作负载还需要设备插件、驱动和相关资源配置。

例如有三台服务器、每台两张 GPU。你提交一个要求 `nvidia.com/gpu: 1` 的推理 Pod，Kubernetes 会根据可用 GPU、CPU、内存和调度约束挑选节点；GPU 设备插件负责让集群看见这些设备资源。Deployment 维护“应该有几个 Pod 正在运行”，Service 则把多个 Pod 组织成稳定的访问入口。模型服务内部的 KV Cache 如何分块、每轮让哪些 Token 执行，仍由推理引擎处理。一个负责**哪些进程在哪里运行**，另一个负责**GPU 上的请求怎样执行**。

假设原本只部署两个模型副本，晚上业务高峰有大量用户访问，运维系统可能根据资源使用量或服务性能指标增加副本。这个过程叫 **Autoscaling（自动伸缩）**。新副本需要先拿到 GPU、加载模型、建立缓存池并执行必要的 **Warmup（预热）**，所以扩容并不会在请求量突然上涨时瞬间完成。

服务启动时也不会马上宣布自己可用。**Readiness Probe（就绪检查）** 可以在模型尚未加载完成时阻止新流量进入；**Liveness Probe（存活检查）** 用于发现需要重启的异常进程。上线新版本时，还可以通过 **Rolling Update（滚动更新）**逐步切换副本，并在指标异常时回滚。

### Ray 在这里解决什么问题？

Kubernetes 管理容器和节点资源，**Ray** 更偏向把 Python 等语言写成的计算任务分发到分布式环境中。Ray 里常见两种抽象：**Task** 表示可以远程执行的函数任务，**Actor** 是带内部状态、可以被反复调用的远程对象。

例如一套模型上线前的验证流程，要依次拉取权重、做量化、启动临时推理服务、跑正确性评测、执行压测，然后汇总结果。你可以把流程拆成任务节点，用 Ray 把它们安排到不同机器。需要长期保持状态的 Worker，也可以用 Actor 管理。

这里可以把系统分成两层：**Kubernetes 决定一组容器服务如何在集群里运行；Ray 决定程序里的分布式任务与 Actor 怎么执行。** 两者在不少工程项目里会组合使用，但不一定每个推理服务都需要同时部署两套系统。

### 一个服务副本和一份模型，可能不是一张卡

负载均衡器（Load Balancer）收到请求后，可以根据副本状态把它分发出去。若每个副本各自运行完整模型，那么不同副本有各自的权重和 KV Cache 池。请求进入某个副本并开始生成后，后续 Decode 通常需要继续访问该副本里的缓存。

如果一份模型通过 TP 切在四张卡上，这四张卡共同组成一个逻辑推理副本。要在另四张卡上再放一个副本，就需要另一组权重和缓存资源。工程里说“八张 GPU 跑两个副本，每个副本 TP=4”，意思就在这里。

上层 API 服务还会根据业务加入鉴权、限流、请求 ID、日志记录以及错误处理。超过速率限制时，服务可能返回 **HTTP 429（Too Many Requests）**；内部不可用或过载时，也可能返回 503 等状态码。像 **FastAPI** 这样的 Python Web 框架可以用来实现 HTTP 接口，但真正的大模型计算仍由后面的推理引擎和 GPU 承担。

## 12. 用户说“今天很慢”，工程师到底查什么？

模型上线之后，性能优化变成了一件持续性的工作。用户只会说“它反应变慢了”，但这个“慢”可能发生在完全不同的阶段。

假设一项聊天业务最近出现了这样的反馈：上午基本一秒就能看到回答，下午却经常要等五秒。GPU 显存使用率很高，平均 GPU 利用率也不低。团队如果只看这两个数字，很难判断应该加卡、改调度，还是换 Kernel。

通常会先把一次请求的耗时拆成几段：

```text
用户发送
   │
   ├─ 网络 / 网关 / API 处理
   ├─ 排队等待 Scheduler 分配资源
   ├─ Prefill 处理输入 ─────────────── 第一个 Token 出现
   ├─ Decode 第 1、2、3……轮 ───────── 后续文字逐渐到达
   └─ 最后一个 Token 返回 ────────── 整次请求结束
```

其中最常见的指标之一是 **TTFT（Time to First Token，首 Token 延迟）**，表示从开始请求计时到收到第一个输出 Token 的时间。它可能包括排队、Prefill 和必要的服务开销，具体起止点要按压测工具的定义确认。

**ITL（Inter-Token Latency，Token 间延迟）** 描述相邻输出 Token 之间的时间间隔。**TPOT（Time per Output Token，平均每个输出 Token 的耗时）** 常用生成阶段的耗时除以后续输出 Token 数来估算，比如一条请求输出 101 个 Token，第一个 Token 在 1 秒时到达，最后一个在 3 秒时到达，那么余下 100 个 Token 用了约 2 秒，TPOT 约为 20 毫秒/Token。

总体响应时间也叫端到端延迟（End-to-End Latency）。一个请求可能 TTFT 很短、后面 Decode 很慢；也可能 TTFT 特别长，真正开始生成后却非常流畅。

例如请求 A 排队 800 ms、Prefill 花 200 ms，于是 TTFT 约 1 s；之后每 20 ms 生成一个 Token，用户会觉得“开头等了一会儿，后面很顺”。请求 B 完全没排队，但输入很长，Prefill 花 3 s，TTFT 就可能达到 3 s；开始 Decode 后每 10 ms 一个 Token，也还是得先等那 3 秒。再看请求 C：TTFT 只有 200 ms，但每个 Token 要 150 ms，长回答会慢得明显。这三个问题对应的优化方向完全不同。

要衡量整个服务，还要看 **Throughput（吞吐量）**，例如每秒完成多少请求（Requests/s）或每秒产生多少输出 Token（Tokens/s）。这两个指标不是一回事：一个请求输出十个 Token 和输出一千个 Token，都会给“完成请求数”贡献 1，但计算量不同。**Concurrency（并发数）** 则表示同一时间有多少请求处于执行或等待处理的状态。

服务还经常统计 **P50、P95、P99 延迟**。例如 P95 为 3 秒，表示在这组样本里约 95% 的请求延迟不超过 3 秒。平均数可能看起来很好，但 P99 很大，说明少量用户仍在经历明显的卡顿。

运营侧还会规定 **SLO（Service Level Objective，服务级别目标）**，比如“95% 的请求首 Token 在 2 秒内出现”。如果只统计达到 SLO 的有效完成工作量，就会谈到 **Goodput（有效吞吐量）**。让 GPU 每秒输出更多 Token 固然重要，但如果大部分用户都超过了延迟目标，这份吞吐量的业务价值会打折。

### 先看指标，再找到慢请求

一套可观测性系统通常有三种互补的信息。

**Metrics（指标）** 记录随时间变化的数字，如请求吞吐量、GPU 显存、排队请求数、KV Cache 占用、TTFT 和错误率。**Logs（日志）** 记录具体事件，例如某条请求被限流、某次模型加载失败、某个 Worker 发生 OOM（Out of Memory，内存不足）。**Trace（链路追踪）** 把同一请求经过的网关、服务、排队、模型执行等阶段连接起来，便于看到时间具体耗在哪里。

比如监控图表发现下午 TTFT 的 P99 猛增，而 Decode 的 TPOT 并没有明显变化。顺着慢请求的 Trace 一查，发现大部分时间都在等调度器分配 KV Cache。这时候直接优化 FlashAttention 的帮助可能很有限，应该先检查缓存容量、长上下文请求数量、抢占次数与服务副本负载。

反过来，如果排队很短、TTFT 也正常，但每个 Token 的间隔越来越大，就可以从 Decode 的权重读取、KV Cache 带宽、GPU 内核耗时或并发批大小继续往下查。

常见监控软件里，**Prometheus** 用来收集和查询时间序列指标，**Grafana** 用来制作仪表盘。跨进程、跨服务的追踪可以使用 **OpenTelemetry** 等标准工具接入。拿到一条慢请求后，工程师就能把它对应的阶段缩小到某个进程或 GPU 执行区间。

### GPU 内核慢在哪里？

当问题已经定位到 GPU，接下来常用 **Nsight Systems** 看 CPU 线程、CUDA API、Kernel 启动、GPU 执行和内存拷贝的时间关系。它适合回答“谁在等谁”“GPU 中间为什么空了一段”“是不是 CPU 提交跟不上”这类问题。

如果某个 Kernel 被确认是热点，再用 **Nsight Compute** 深入分析它的执行效率，例如访存吞吐量、SM 使用情况、Occupancy、Warp Stall（线程束停顿原因）、缓存命中与指令执行特征。热点是矩阵乘法，就检查 Tensor Core 使用与数据布局；热点是 Reduction 或 Softmax，就检查共享内存、访存模式和寄存器压力。

实际优化通常有一条很朴素的顺序：先知道慢的是哪段，再知道那段时间主要花在计算、访存、通信还是启动开销，最后才调整代码和配置。

例如同样是吞吐量不足，可能分别需要不同的办法：

- **KV Cache 不够：** 改善缓存分配、缩短上下文、降低 KV 精度，或者增加 GPU/副本资源。
- **Attention 中间数据搬运太多：** 检查 FlashAttention 等 IO 优化内核。
- **每轮 Decode 的 Kernel 启动频繁：** 检查 CUDA Graph 与算子融合。
- **长 Prefill 把 Decode 挤得不稳定：** 调整 Chunked Prefill 或考虑 PD 分离。
- **专家分布不均：** 检查 MoE 路由与 EP 通信、专家热点。
- **多 GPU 同步占时太长：** 检查 TP/PP/EP 拆分方式、NCCL 与网络拓扑。

这些情况在真正的集群里可能同时存在。优化其中一项后，新的瓶颈又会显露出来，因此负载测试要使用和业务接近的输入长度、输出长度、请求到达模式与并发水平。

## 13. 回到最初的聊天窗口

我们一开始发出去的是一句很普通的问题：“为什么大模型有时回答得很慢？”

现在可以沿着同一条请求，把整套系统串起来。

消息经 API 到达服务器，调度器检查是否有足够的计算预算和 KV Cache 让它进入执行。输入经过分词和 Embedding，被送进 Transformer。Prefill 一次处理已有的输入序列，生成第一个 Token，并把历史 K、V 保存下来。

接下来的 Decode 每次处理新的位置，持续读取历史 KV Cache。推理引擎用 PagedAttention 一类的机制管理不断增长的缓存，用 Continuous Batching 在不同请求之间动态安排 GPU 时间；遇到长输入，可以把 Prefill 拆成多轮，避免让已经在生成的请求长时间停顿。

到了 GPU 内部，Tensor Core、CUDA Kernel、各层缓存和 HBM 一起决定了运算能跑多快。FlashAttention 设法少搬一些中间数据，CUDA Graph 设法少做一些重复提交工作。模型太大时，可以考虑量化、GQA、MLA，或者把模型用 TP、PP 等方式分到多张 GPU 上。服务规模进一步增大，就会用到多副本、负载均衡和分布式资源管理。

而所有这些计算能力，最终都来自此前训练得到的权重：训练框架组织前向与反向传播，多卡并行和集合通信共同完成参数更新，检查点与评测保证这份模型能够持续迭代，并且可以被稳定地交付给线上服务。

把这条链路放在一起看，AI Infra 大致围绕三件事展开：模型的计算能正确执行，相同的工作尽量少花资源，用户数量增加时服务依然稳定。每次遇到新技术，只要知道它改善的是哪一段、付出了什么代价，就能看懂它在整个系统中的位置。
