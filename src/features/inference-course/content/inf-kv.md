## 缓存了什么

模型权重在请求之间通常保持不变，但每条请求的上下文不同。随着输入和生成过程增长，模型要保存更多历史位置的 Key、Value，这部分就是 KV Cache。

在带因果注意力的自回归推理中，已经处理过的位置不会因为后来追加 token 而读到新的未来内容。保持同一模型与相关配置时，这些位置的 K/V 可以复用。新位置计算自己的 Q、K、V，将新 K/V 接到缓存中，再用新 Q 读取相关历史 K/V。

```atlas-demo
kv-flow
```

缓存不等于保存整次推理的所有中间量，也不表示后续生成不用再读历史内容。模型仍要运行新位置经过的各层计算；Attention 仍要使用相关的历史 K/V。

## 从一个位置推导显存

先假设每层使用相同的 KV 头数和 head 维度，缓存采用相同精度，全上下文保存，无跨请求共享，也不做张量并行分片。以下例子适用于这种普通 MHA/GQA/MQA 缓存估算，不直接适用于 MLA、滑动窗口、混合层或压缩缓存。

取一个已处理的 token、一个层：K 和 V 各有 `KV heads × head dim` 个元素。两者相加，再乘每个元素的字节数，就得到该位置该层的数据量。

| 扩展范围 | 本例的计算 | 结果 |
| --- | --- | ---: |
| 一个位置、一个层 | 2 × 8 个 KV heads × 128 × 2 字节 | 4096 字节 |
| 一个位置、32 层 | 4096 × 32 | 128 KiB |
| 一条 4096 位置序列 | 128 KiB × 4096 | 512 MiB |
| 16 条同长度序列 | 512 MiB × 16 | 8 GiB |

前面的 2 对应 K 和 V；最后的 2 字节来自 BF16。GQA 模型这里使用 **KV 头数**，不能用查询头数替代。如果每层配置不同，应逐层求和，而不是统一乘层数。

## 改变长度和并发，检查结果

下面沿用 32 层、8 个 KV heads、head dim 128、BF16。每个请求的缓存长度相同；计算只覆盖原始 KV 数据，未计权重、工作区、分配与框架开销。它不是可承载并发预测器。

```atlas-demo
kv
```

可以先预测再调整：长度翻倍、并发不变时，KV 数据量翻倍；长度和并发都翻倍时，变成四倍。不同请求长度不同时，应按各请求缓存位置数求和，不能默认全部达到最大上下文长度。

用 Python 复核默认例题：

```python
layers, kv_heads, head_dim = 32, 8, 128
bytes_per_element, tokens, sequences = 2, 4096, 16
per_sequence = 2 * layers * kv_heads * head_dim * bytes_per_element * tokens
print(per_sequence / 1024**2)             # 512.0 MiB
print(per_sequence * sequences / 1024**3) # 8.0 GiB
```

## 为什么监控里的显存对不上

上面的 8 GiB 只是这一组请求的 KV 数据估算。实际设备还存有权重、激活和临时工作区；框架可能保留内存池，引擎也可能预先分配缓存块。监控中的已分配内存不等于当前请求实际写入的 K/V 字节。

例如看到显存长期占满，并不能单凭这个数判断泄漏；要结合分配策略、缓存使用率、请求结束后的资源回收和失败日志分析。同样，不能用“总显存减去 8 GiB”直接判断某个模型是否能运行。

## 分页管理改变了什么

假设每块存 4 个位置的 K/V，一个请求已处理 9 个位置，需要 3 块。逻辑块可以映射到物理块 7、2、5；最后一块只用 1 个位置，还有 3 个空位。

| 逻辑块 | 物理块（示例编号） | 占用 |
| --- | ---: | --- |
| 0 | 7 | 位置 0–3，已满 |
| 1 | 2 | 位置 4–7，已满 |
| 2 | 5 | 位置 8，剩 3 格 |

接下来的 3 个位置可以填入末块，再增长才需要申请新块。块表负责让计算找到对应物理位置。这里 4 只是教学块大小，真实引擎配置应查版本文档。

分页降低连续大块预留造成的浪费，并让共享更方便；**它不会让相同配置下每个 token 的 K/V 元素自动变少**。末块仍可能未填满，不能把“减少浪费”理解为没有任何额外开销。

## 前缀共享与估算边界

两个请求若包含完全一致、可复用的前缀，系统可能复用相应缓存块，减少重复 prefill 和重复存储。是否可复用还与模型、token 序列、聊天模板、缓存实现和隔离策略有关。视觉上相似的文字未必编码相同。

本节计算器没有模拟共享。KV 量化会改变每元素的数据量并带来额外参数和精度问题；分布式推理还要考虑切分或复制方式。分析这些情况时，应先重写估算假设，再比较实测。

## 练习与排查顺序

练习：沿用固定配置，把 16 条、4096 位置改成 8 条、8192 位置，原始 KV 数据量是多少？

```atlas-answer
仍是 8 GiB，因为总缓存位置数相同。但不能推断两者吞吐和延迟相同：请求长度、计算形状和调度条件已经改变。
```

如果真实服务 OOM，先记录模型和精度、输入输出长度、运行并发、最大上下文、KV 配置及报错阶段；再区分模型加载、prefill、decode 或临时工作区的峰值。下面的实验入口可测量上下文与缓存变化，没有 GPU 时先完成上述手算即可。
