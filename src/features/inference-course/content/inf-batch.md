## 短请求结束后，空位能否接下一个请求

假设一次最多处理两条序列。请求 A 需要 2 轮 decode，请求 B 需要 5 轮，还有请求 C 等待运行。A 结束后，B 还没结束；如果必须等整批结束才能接入 C，就会留下闲置位置。

连续批处理在生成的迭代边界重新组织批次，让已完成的序列退出、等待中的序列在资源允许时加入。它关注的是**何时重新组成批次**，与 API 是否支持流式返回是不同问题。固定批次里的短请求也可以提前返回结果，不能把它说成必然被长请求“扣住答案”。

固定批次：先处理 A、B，A 在第 2 轮结束；空位等待到第 5 轮 B 结束。C 在第 6–7 轮运行。

连续批处理：A 在第 2 轮结束；C 从第 3 轮进入空位，在第 4 轮结束；B 到第 5 轮结束。整个集合由 7 轮缩短到 5 轮，但 A 和 B 本身没有因此少做计算。

## 为什么真实系统没有这么简单

真实请求需要先做 prefill。新请求进入时不仅占一个序列位置，还要占用计算预算和 KV Cache。长输入可能给正在 decode 的请求带来等待，影响后续 token 间隔。

Chunked prefill 将长输入分成较小片段，在调度时安排这些片段与 decode 的工作。但具体混合方式和预算取决于引擎版本。不能把一张简化时间线当作所有引擎的调度实现。

## Batch 变大为什么未必人人更快

批次增大可能提高权重读取等工作的复用，带来吞吐收益；同时会消耗更多缓存，并改变单步计算耗时、排队和尾延迟。总 tokens/s 上升时，某些请求的首 token 或后续 token 间隔仍可能恶化。

因此至少同时观察：请求到达率、等待队列、运行序列数、输入输出长度分布、TTFT、token 间隔以及成功率。还要区分“最多允许运行多少条”和“客户端同时发出多少请求”，这两个限制不是同一个参数。

## 显存不足时，调度也要改变

当缓存空间不够时，引擎可能拒绝接纳新序列、让其等待，或抢占已有序列并稍后恢复。有的恢复方式需要重算，有的实现或配置支持换出。具体行为应看引擎版本和日志，不能默认一定有某种策略。

持续提高并发可能导致抢占和重算增多，抵消吞吐收益。排查时记录缓存使用、抢占事件及队列，往往比只看 GPU 利用率更有帮助。
