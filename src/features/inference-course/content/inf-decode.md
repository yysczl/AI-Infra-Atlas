## 从一个输入开始

设输入已被编码为三个 token `[a, b, c]`，模型要接着生成三个 token `[d, e, f]`。它不会一开始就知道 d、e、f，必须先预测 d，再把 d 作为下一轮输入的一部分，逐步预测后面的内容。

这里讨论带因果注意力的自回归语言模型。一次请求通常分为 prefill 和 decode 两段，但调度、传输和结果处理也会占时间。

```atlas-demo
decode
```

## Prefill：处理已有输入

Prefill 将输入 `[a, b, c]` 送入模型。虽然存在因果依赖约束，已知输入的位置仍可通过带 mask 的矩阵运算并行处理。模型为这些位置计算各层表示与 K/V，最后一个输入位置的输出用于预测第一个新 token d。

因此，首 token 通常在 prefill 之后产生。此时 KV Cache 存的是已经送入模型的 a、b、c；刚采样得到的 d 尚未被送入下一轮，所以它的 K/V 不一定已经存在。

## Decode：每轮推进一个新位置

下一轮只需为新位置 d 计算表示，读取已缓存的历史 K/V，并预测 e；再处理 e，预测 f。常规逐 token decode 的过程可以写成：

| 本轮送入模型 | 读取的历史缓存 | 本轮新增缓存 | 本轮预测 |
| --- | --- | --- | --- |
| a、b、c | 无 | a、b、c | d |
| d | a、b、c | d | e |
| e | a、b、c、d | e | f |

如果生成在 f 结束，就无需为了再预测一个 token 而把 f 送入模型。这也是估算缓存时应说清“已处理 token 数”，而不是机械地把最终文本长度代入的原因。

缓存消除了历史位置的部分重复计算，但新的查询仍需要读取相关历史 K/V。对话变长，decode 的读取量和缓存占用也可能增长。

## 生成不只有矩阵乘法

模型输出通常是词表上的 logits。采样或贪心选择据此得到下一个 ID，再检查停止条件，例如 EOS 或最大输出 token 数。流式服务还需要把新结果编码并通过网络发给客户端。

因此，固定模型和 prompt 后，温度、随机种子、停止规则及输出长度上限都可能改变结果或耗时。比较两次实验时要保存这些配置，不能把输出更短直接解释为引擎更快。

## 三个时间指标怎样读

以下是教学构造的客户端时间线，单位毫秒，不代表任何模型的速度。

| 事件 | 相对发起请求的时刻 |
| --- | ---: |
| 请求发出 | 0 |
| 收到第一个 token | 240 |
| 收到第二个 token | 280 |
| 收到第三个 token，完成 | 340 |

这次请求 TTFT 为 240 ms，端到端延迟为 340 ms，两个后续 token 间隔分别是 40、60 ms。若使用“首 token 之后的时间除以剩余 token 数”的口径，平均 TPOT 为 `(340 - 240) / (3 - 1) = 50 ms`。

TTFT 包含客户端观察到的排队、网络和 prefill 等时间，不能直接当成纯 GPU prefill 时间。TPOT 也不同于每个 token 间隔的完整分布；平均值会掩盖某一次明显停顿。不同工具对 token 数、流式块和时间戳的处理可能不同，比较前先核对定义。

## 长输入和长输出分别改变什么

长输入通常增加 prefill 工作和初始缓存量，首先影响 TTFT。长输出增加 decode 轮数，通常拉长端到端时间并让缓存继续增长。具体瓶颈还取决于 batch、模型、硬件和调度；“prefill 计算受限、decode 带宽受限”只能作为常见起点，不能代替测量。

练习：比较“4096 输入、32 输出”和“32 输入、512 输出”。只给平均请求耗时，能判断哪个引擎更好吗？

```atlas-answer
不能。两组请求工作量不同，应该固定输入输出分布，分别观察 TTFT、token 间隔、端到端延迟、吞吐和错误率。即使平均端到端时间相同，用户等待首字和等待后续内容的感受也可能不同。
```
